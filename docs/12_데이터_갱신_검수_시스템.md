# 데이터 자동 점검 + 검수 시스템 (2026-11-24)

> 매일 아침 안산시청 고시·공고를 확인한다. **원문으로 확인된 기간 업데이트는 자동으로 바로 반영**하고, **새 사업은 자격조건까지 자동으로 채워 PR에 넣어서 사람은 Merge(최종 승인)만** 한다. 폐기·확인할 것만 사람이 고른다.
> 판정(충족·미충족)은 그대로 `judge.js` 규칙이 하고, LLM은 "공고 정리"만 맡는다.

## 1. 전체 흐름

```
매일 06:40 (GitHub Actions: data-check.yml)
  ① 고시·공고 새 글 수집 ─ 하루 20건 안팎, 대부분 공시송달·도로점용 같은 행정 공고
  ② 제목 규칙으로 1차 거르기 ─ 모집·공모·신청 공고만 (600건 중 약 30건)
  ③ 원문 + 첨부(hwp·pdf 미리보기) 읽기
  ④ 분류: 무료 SLM(Open AI Service Hub) → 실패하면 규칙
       이미 있는 공고 → 버림 / 기존 사업 새 회차 → 기간 업데이트 / 처음 보는 청년 사업 → 추가 후보
  ⑤ 기존 사업 점검: 예상 모집 시기 지남 → 확인 / 1년 넘게 새 회차 없음 → 폐기 검토 / 날짜 없음 → 분기마다 확인
  ⑥ 기간 업데이트 중 아래 조건을 모두 채우면 → src/overrides.auto.json 에 기록하고 main에 바로 커밋 (사이트 자동 반영)
       · 신청기간 날짜를 원문에서 규칙으로 직접 확인함 (LLM이 낸 날짜만으로는 안 됨)
       · 기존 사업과 이름 유사도 0.75 이상
       · 나이·거주 조건이 지금 데이터와 같음
       · 지금 데이터보다 새 회차 (마감일이 더 늦음)
  ⑦ 새 사업 중 SLM이 거주 유형·나이·신청기간·혜택을 다 채우고 근거 문장이 원문에 있으면
       → src/overrides.new.json 에 넣어 "데이터 검수 요청" PR에 포함 (Merge 하면 추가)
  ⑧ 나머지(다 못 채운 새 사업, 폐기·확인)는 review/queue.json 으로 같은 PR에 (브랜치 data-review)

사람 (최종 판단만)
  ⑨ PR 본문에서 "Merge 하면 추가" 새 사업을 훑어보고 괜찮으면 → PR Merge = 최종 승인, 끝
  ⑩ 빼거나 고칠 것·폐기·확인 항목이 있을 때만: 검수 화면(https://chang-kyu.github.io/aix-teamplay/review/)에서 고르고
     overrides.json 을 data-review 브랜치의 src/ 에 올린 뒤 Merge
```

## 2. 파일

| 경로 | 내용 |
|---|---|
| `src/update/board.py` | 안산시청 고시·공고 목록·상세·첨부 미리보기 읽기 (표준 라이브러리만) |
| `src/update/rules.py` | 제목 1차 필터, 기존 사업 이름 맞추기, 신청기간·나이·거주요건 뽑기, 원문 인용 확인 |
| `src/update/llm.py` | OpenAI 호환 API로 공고 분류 (기본: Open AI Service Hub, `exaone-4.0-32b`) |
| `src/update/check.py` | 매일 실행하는 본체. 대기열·요약·본 글번호 저장 |
| `src/update/test_update.py` | 테스트 (실제 안산시청 글로 만든 fixtures 사용, 인터넷 없이 실행) |
| `src/overrides.auto.json` | **자동 반영한 기간 업데이트**. 매일 점검이 main에 바로 커밋 |
| `src/overrides.new.json` | **자동으로 다 채운 새 사업**. 검수 PR에 들어가 있다가 Merge 되면 main에 들어감 |
| `src/overrides.json` | **사람이 검수에서 승인한 결정**. 자동 반영보다 우선 (틀린 자동 반영은 여기서 고치면 덮어씀) |
| `review/index.html` | 검수 화면 |
| `review/queue.json`, `review/SUMMARY.md` | 검수 대기열, PR 본문 |
| `state/seen.json` | 마지막으로 본 글번호 |
| `.github/workflows/data-check.yml` | 매일 점검 → 검수 PR |
| `.github/workflows/rebuild.yml` | 데이터가 바뀌면 다시 빌드 + 테스트 |

원본 데이터(`build_v3.py` 안의 52건)는 건드리지 않는다. `build_v3.py`가 원본 → 자동 반영 → 준비된 새 사업 → 사람 결정 순서로 덮어쓴다 (사람이 '무시'한 새 사업은 빠짐). 바뀐 것은 전부 두 파일에 남아서, 언제 누가 무엇을 바꿨는지(`decided`, 메모) 추적할 수 있다.

## 3. 환각 막는 장치

- LLM이 "원문 인용"이라고 준 문장이 실제 원문에 없으면 버리고, 규칙이 찾은 원문 조각으로 대신한다. 검수 화면에 ✓/✗로 표시.
- LLM이 고른 거주 유형이 애매하면(R9) 사람이 고르기 전까지 **반영 버튼이 잠긴다**.
- 승인된 결정만 데이터에 들어가고, 빌드 후 테스트가 실패하면 사이트에 올라가지 않는다.
- LLM 호출이 실패하면(키 없음·한도·오류) 규칙으로 계속 돈다. 하루 호출은 최대 60회 (`LLM_MAX_CALLS`, 무료 한도 500회).

## 4. 처음 한 번 설정 (저장소 주인)

1. **Settings → Actions → General → Workflow permissions**: "Read and write permissions" 선택, "Allow GitHub Actions to create and approve pull requests" 체크
2. **Settings → Secrets and variables → Actions**
   - New repository secret: `LLM_API_KEY` = Open AI Service Hub 개발키 (`sk-dev-…`). 없으면 규칙만으로 돈다.
   - (선택) Variables: `LLM_MODEL` (기본 `exaone-4.0-32b`, 다른 후보 `kanana-2-30b-a3b`, `hyperclovax-seed-32b`)
3. **Actions 탭 → "데이터 점검 (매일)" → Run workflow** 로 첫 실행. 첫 실행은 최근 30일 치를 본다.
4. 몇 분 뒤 "데이터 검수 요청" PR이 생기면 검수 화면에서 확인.

개발키는 채팅이나 코드에 넣지 말고 Secret에만 넣는다.

## 5. 사이트를 못 읽을 때

정부·지자체 사이트는 해외 IP 접속을 막기도 한다. GitHub Actions 서버는 해외에 있어서, PR 본문에 "⚠️ 안산시청 사이트를 읽지 못했어요"가 뜨면:

- **팀원 PC에서 실행**: `cd src && python -m update.check` (파이썬 3.10+, 설치할 패키지 없음). 생긴 `review/queue.json`, `state/seen.json`을 data-review 브랜치에 올리면 된다.
- **자체 실행기(self-hosted runner)**: 팀원 PC를 GitHub Actions 실행기로 등록하고 `data-check.yml`의 `runs-on: ubuntu-latest`를 `self-hosted`로 바꾸면 매일 자동으로 돈다.

## 7. 자동 반영이 틀렸을 때

PR 본문의 "✅ 자동 반영한 기간 업데이트" 표에서 확인한다. 틀렸으면 검수 화면이나 `src/overrides.json`의 `updates`에 같은 사업 id로 올바른 값을 넣으면, 사람 결정이 자동 반영보다 우선이라 덮어쓴다. 자동 반영을 끄려면 `data-check.yml`의 `python -m update.check`에 `--no-auto`를 붙인다.

## 챗봇(AI 도우미)과 빌드

- 화면 코드는 `src/web/template.html` 하나가 원본이에요. 루트 `index.html`·`template.html`은 빌드 결과라서 **직접 고치면 다음 자동 빌드 때 덮어써져요.** 화면을 고칠 땐 `src/web/template.html`을 고쳐서 올리면 Actions가 다시 빌드해요.
- 챗봇 자료를 만드는 코드는 `src/rag/`에 있어요(경운 작성, 자세한 건 `src/rag/README.md`).
  - `CORPUS` ← `python rag/build_corpus.py` → `src/corpus_v3.json`
    - `policies_v3.json`을 읽어서 만들기 때문에 자동 갱신된 기간·새 사업이 챗봇에도 그대로 들어가요.
  - `EMB` ← `node rag/build_embeddings.mjs` → `src/embeddings_v3.json`
    - 의미 검색용이에요. 브라우저와 같은 transformers.js로 만들어야 해서 Node.js를 써요.
- 빌드 순서: `python build_v3.py` → `bash rag/rebuild.sh` → `python web/build_web.py`
  - `rebuild.sh`는 CORPUS를 매번 다시 만들어요.
  - EMB는 CORPUS가 지난번과 달라졌을 때만 다시 만들어요(모델 111MB, 1~2분). Actions에서는 모델을 캐시해 둬요.
  - EMB를 못 만들면 경고만 내고 의미 검색을 뺀 채 빌드해요. 기본 낱말 검색은 최신 데이터로 동작해요.
- 자동으로 추가된 새 사업은 `build_corpus.py`의 `EXTRA`(신청 방법·문의처·검색어 같은 설명)가 없어요. 그래서 기본 정보만으로 챗봇 자료가 만들어져요. 필요하면 `EXTRA`에 그 사업을 추가해 주세요.
- 새 사업의 거주 조건에 기준일이 없으면 "신청일 기준"으로 채워요. R2(거주 연수)·R6(학교·직장)은 자동 추가하지 않고 사람이 확인해요.
